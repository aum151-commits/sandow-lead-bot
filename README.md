## Диалог — короткий путь к контакту

Новый гость: вход → предложение с тренировкой и экскурсией → номер → выбор формата.
До номера нет вопросов о целях или направлениях. Действующее меню членов клуба не меняется.

- Тренировка: задача → направление (для специальных задач пропускается) → действующий календарь → подтверждение.
- Экскурсия: необязательный множественный выбор интересов или «Пока не знаю» → календарь → подтверждение сотрудником.
- Групповые программы доступны как интерес к экскурсии, но не как персональная тренировка.
- Подтверждение не означает фактический визит или покупку. Предварительная запись явно отличается от подтверждённой.
- Исторические сообщения недошедшим не запускаются без проверки визитов, покупок и будущих записей.

### Учёт и безопасный отчёт

Шаги новой воронки сохраняются в `data/tg_funnel.json` через действующее хранилище бота.
Для отчёта используйте доверенную локальную выгрузку этого файла; выгрузки с данными пользователей
не добавляйте в репозиторий. `report_direct_response.py` читает только локальный файл,
не обращается к сети и не показывает имена, телефоны или идентификаторы пользователей.

```text
python report_direct_response.py <local-export.json> --since 2026-11-22 --until 2026-11-29
python -m unittest test_report_direct_response -v
```

Отдельно показываются две когорты: первый запуск в периоде (включая не дошедших до предложения)
и первый показ предложения в периоде. Время московское; конец периода не включается.
Считаются уникальные гости, контакты, записи, подтверждения, форматы и действия после возвратного сообщения.
Действующие члены и записи с признаком проверки исключаются. Формат по умолчанию не считается выбором.
«После сообщения» означает порядок событий, а не доказанный эффект сообщения.
Визиты, покупки и переход «нажатие мессенджера → запуск» требуют отдельных подтверждённых источников;
отчёт не подменяет их событиями переписки. Данные старого пути не выдаются за исходную когорту нового.

**Время (правки Ольги 02.10.2026) — три разных набора:**

| Кто выбирает | Часы | Сколько |
|---|---|---|
| Новый гость, подарочная тренировка | 10:00–20:00, каждый час | 11 |
| **Действующий член клуба, тренировка** | **07:00–22:00, каждый час** | **16** |
| Экскурсия по клубу | 10:00, 12:00, 14:00, 17:00, 19:00, 21:00 | 6 |
| Окна тренеров (что они отмечают) | 07:00–22:00, каждый час | 16 |

Почему у члена клуба шире, чем у нового гостя: у члена доступ 24/7, и для
раннего утра или позднего вечера присутствие менеджера и координатора не
нужно. Новый гость приходит на первую ознакомительную тренировку — её ведём в
рабочие часы.

**Инвариант, который нельзя терять:** сетка члена клуба и сетка гостя обязаны
быть внутри окон тренеров (`SLOTS_MEMBER == SLOT_LIST`, `SLOTS_TRAINING ⊂
SLOT_LIST`). Координатор подбирает эксперта сверкой выбранного времени со
свободными окнами (`_free_trainers_for`), и час, которого нет в кнопках
тренера, ломает этот подбор — вместо выбора тренера остаётся слепая кнопка
«Подтвердить время». После правки любой из сеток — прогнать проверку
(`python test_okna_i_daty.py`, блок 12).

На частые вопросы (цена, бассейн, адрес, режим, сауна, тренеры) бот отвечает сам и
возвращает к заявке. Цены не называет — только разовое посещение 990 ₽.

Один человек — одна заявка в сутки, чтобы менеджеров не заваливало.

## День записи: настоящие даты, а не «Пн» (исправлено 08.10.2026)

**Что было сломано.** Кнопки дней назывались днём недели, а бот разворачивал
«Пн» в БЛИЖАЙШЕЕ вхождение понедельника. В понедельник это означало сегодня —
и клиент, который хотел записаться на следующий понедельник, попадал на день
отправки сообщения. Дата нигде не называлась, поэтому ошибку нельзя было
заметить ни клиенту, ни менеджеру.

**Как теперь.** Клиент видит кнопки с датами: «Сегодня, чт 08.10», «пт 09.10»,
… «чт 15.10». Выбранная дата едет дальше ISO-строкой (`tp:2026-10-15:training`),
поэтому двусмысленности нет ни в боте, ни в карточке менеджеру, ни в заявке 1С:
время везде пишется как «четверг, 15 октября, 10:00». Старые сообщения с днём
недели не угадываются — бот просто перерисовывает выбор дня.

Заодно перестали показываться прошедшие часы сегодняшнего дня: раньше человек
в 20:30 мог выбрать «10:00», и это попадало в заявку.

## Окна тренеров — на всю неделю записи (08.10.2026)

**Горизонт.** `HORIZON_DAYS = 7` в `bot.py`: записаться можно на сегодня (если
на нём остались непрошедшие часы) и на 7 дней вперёд. Тренеры отмечают окна
ровно на те же даты — иначе на дальние дни координатор не найдёт кандидатов и
вместо выбора тренера получит слепую кнопку «Подтвердить время». Менять
горизонт — одним числом, но тогда же проверять, что список дат у клиента и у
тренера по-прежнему один и тот же (`horizon_dates`).

| Что делает тренер | Где |
|---|---|
| Регистрация (ссылка `?start=trainer` от Ольги) | один раз выбирает своё имя |
| Свои окна на неделю | кнопка «🗓 Мои окна на неделю», команда `/okna` или кнопка в вечернем сообщении |
| Отметить/снять час, «Занят весь день» | кнопки дня |
| «📋 Так же на всю неделю» | переносит набор часов этого дня на остальные дни внутри горизонта (занятые гостями часы не возвращает в свободные) |
| Вечерняя сверка 21:00 | «Завтра, вт 13.10 — 3 окна: 10:00, 11:00, 12:00. Если что-то изменилось, поправьте; если всё в силе — подтвердите одним нажатием» |
| Утреннее напоминание 9:00 | только тем, кто ещё не открыл окна на сегодня |

Вечернее сообщение теперь уходит ВСЕМ зарегистрированным тренерам, включая тех,
кто уже отметился (раньше такие молчали, и поправить дальние дни было нечем).
«✅ Всё в силе» ставит отметку `confirmed_at` — координатор в утренней сводке
видит галочкой, кто подтвердил. В 9:30 координатору уходит сводка: сегодня и
завтра подробно, на остальные дни — сколько тренеров открылось.

Данные — `data/trainer_slots.json` в приватном репозитории; прошедшие дни
чистятся раз в сутки вместе с вечерней рассылкой.

2. Подставить токен в переменную `TELEGRAM_BOT_TOKEN` сервиса на Render.

   `https://api.telegram.org/bot<ТОКЕН>/setWebhook?url=https://sandow-lead-bot.onrender.com/tg/<HOOK_SECRET>`

   `yandex-business-automation` (скрипт правит виджет и футер, затем публикует).

## Выкатить изменения

**Исправлено 02.10.2026 — раздел указывал не на тот сервис.** Живой бот живёт
на **отдельном** аккаунте Render: сервис `sandow-lead-bot-standalone`

`sandow-lead-bot-v2` (`srv-dame10ad0e5s73f35qi0`, ключ `RENDER_NEW_API_KEY`)
оставлен на случай отката: деплой туда живого бота **не меняет**. Проверено
через API Render — список сервисов по каждому ключу.

`autoDeploy` НЕ работает так, как когда-то здесь было написано: сервис
деплоится из Docker-образа `ghcr.io/aum151-commits/sandow-lead-bot:latest`,
а не напрямую из исходников. Просто `git push` ничего не меняет на живом
сервисе, пока образ не пересобран.

**Всё это делает один скрипт** (в папке `yandex-business-automation`):

```
python -m src.rpa.deploy_lead_bot                 # выкатить
python -m src.rpa.deploy_lead_bot --только-проверка   # только сверить файлы
```

Он сверяет местный `bot.py` с репозиторием, отказывается работать, если в
репозитории более новый код, затем: пишет файл → пересобирает образ → деплоит
на Render → ждёт, пока `/health` отдаст новую версию.

Ручной порядок — тот же, если понадобится по шагам:

1. Файл `bot.py` в github.com/aum151-commits/sandow-lead-bot (ветка `main`).
   Локальная папка `D:\Проекты\sandow-lead-bot` **не привязана к этому
   репозиторию** (`git remote` пуст) — она часть общего автосохранения
   `D:\Проекты`, поэтому push идёт через GitHub API, а не `git push`.
2. Пересобрать образ: `POST` без тела на
   `https://api.github.com/repos/aum151-commits/sandow-lp/actions/workflows/build_images.yml/dispatches`
   с `{"ref":"main"}`, токен — `GITHUB_TOKEN_WORKFLOW` из `.env`
   (`yandex-business-automation/.env`). Занимает около минуты, проверить
   через `.../actions/workflows/build_images.yml/runs?per_page=1`.
3. Задеплоить новый образ: `POST` на
   `https://api.render.com/v1/services/srv-dat63l942hec73fldsd0/deploys`
   с `{"clearCache":"do_not_clear"}`, токен — `RENDER_STANDALONE_API_KEY`.
4. Проверить `/health`: поле `version` должно смениться (бампать `VERSION`

## Про бесплатный тариф

Render усыпляет сервис после 15 минут тишины, пробуждение около 40 секунд. Задача
планировщика «Сандов - бот лидов не спит» пингует его каждые 10 минут с 8:00 до
23:00 — но только когда ноутбук включён. Ночью бот спит намеренно: так хватает
750 бесплатных часов в месяц на два сервиса вместе с голосовым тренажёром.

Совсем убрать задержку можно внешним пингером (cron-job.org, UptimeRobot) —
нужна регистрация по почте.
